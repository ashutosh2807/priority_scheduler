Connected and monitoring modes

Operational pages show whether Oracle execution is enabled. In monitoring mode, the worker evaluates your configured schedules and queue; existing results remain visible, but no procedure is run. Confirmations, queue changes and runbook edits are still saved.

If the connection is unavailable, start the combined portal and scheduler launcher. Calendar source notices explain when holiday data is using a retained snapshot. The last working report date and the T−1 publication cutoff are shown separately. Future entries do not advance the published report date.

Add, edit and delete schedules

A SUPERUSER can open Schedules and choose Add schedule, or open an existing schedule and choose Edit schedule settings. Configure the procedure, frequencies, execution rules, attempt limit, confirmation owner, cover and operating guide in one place.

In Oracle mode, saves go to SCHEDULE_EXTRACT_MASTER and refresh the worker's snapshot. There is no JSON file to maintain manually. UI schedule changes refresh the snapshot immediately. Automatic Schedule Master refresh defaults to once an hour, independently of the daily DATEMAST read. Changes made directly in Oracle become visible after the next refresh. The portal shows execution status and history reported by the worker.

Delete schedule asks for its exact name and an audit reason. Running schedules must finish first. Deletion retains execution history, work logs and audit records. IDs cannot be reused.

Start your day

  1. Open Day-wise tasks and choose the operating date.
  2. Review pending, confirmation, running and failed work. “Assigned to me” shows your confirmation responsibility.
  3. Open a task to review its business report date, expected time and step-by-step guide.
  4. Record human checks in the runbook. The worker reports whether execution actually succeeded.

Calendar and T+1

Calendars mark Sundays and 2nd/4th Saturdays as default bank holidays. The 1st/3rd/5th Saturdays are working days unless another holiday applies. Working Saturdays are labelled separately. Approved leave and tasks stay visible on holidays because some schedules permit holiday execution.

Oracle DATEMAST contains working dates only through T−1. The loaded range rolls from 31 March of the previous financial year through today; for example, on 12/09/2026 it covers 31/03/2025 to 12/09/2026. The calendar shows both this loaded range and the past dates assessed through T−1. Within the assessed history, a present entry confirms a working day and a missing date indicates a holiday. For example, on the 10th, the 9th is present if it was working; absence of the 10th is expected. Older dates outside loaded history, today and future dates use provisional bank defaults; missing DATEMAST entries do not mark them as holidays. A report’s business date remains unchanged when execution moves to a later working day. The calendar groups work by operating day and shows the business date on every row. Future rows are forecasts, subject to DATEMAST availability, holidays, confirmation and execution windows.

DATEMAST is checked once each day and on worker startup. After a same-day database correction, a SUPERUSER can choose Refresh from Oracle on the calendar. Failed refreshes show a warning and retry safely. For T+1 work, execution moves to the next allowed working day and waits for the required DATEMAST threshold. SAME_DAY uses the current day, subject to the worker’s configured holiday policy. The worker owns these decisions; this portal displays them.

Whose confirmation is needed?

A SUPERUSER assigns the primary confirmation operator and optional preferred backup. Only the effective available assignee can confirm the current occurrence. Confirmation for one report does not approve future reports.

  1. The available primary operator remains responsible.
  2. During approved leave, an available nominated leave cover takes over.
  3. If nominated cover is unavailable, the preferred backup is used.
  4. Otherwise an active, available operator is selected in employee-ID order. If none is available, the task shows “Cover required”.

Request leave under Leave & coverage. You may nominate cover before SUPERUSER approval. Approval rechecks availability and assigns available cover for gaps. Only approved leave changes availability; the primary assignment is retained. Unavailable cover is resolved again on the day, and the actual confirmer and assignment source are audited.

Manage the live priority queue

The queue contains tasks that have passed the worker’s eligibility checks. Active operators can move entries with the Up and Down buttons and save the order. A changed queue must be refreshed before saving again.

Pause prevents future selection; resume allows reevaluation. Cancelling requires a reason. Running Oracle calls are allowed to finish. Queue changes do not interrupt a running procedure or bypass date, confirmation or retry rules.

The worker checks on its configured cycle, normally every three minutes. The expected time is an estimate or an eligibility window; queue position is not a guaranteed start time.

Runbooks, expected duration and audit

The primary operator or SUPERUSER can edit descriptions, ordered guide steps and expected execution duration. Ownership changes are restricted to SUPERUSER. Mark each human check against its report date and add operational notes. Reopening a step is recorded too.

The audit log records the actor, time, action, reason and changed values. Runbook checks do not mark Oracle work successful. Execution history comes from the worker. When a running task exceeds the estimate, the daily workspace highlights it for review.

Statuses and recovery

Pending / Confirmation
Waiting for a date, source availability, time window or named operator.
Ready / Running
Waiting in the queue / currently executing.
Done / Failed
The worker has reported the execution outcome. Review the attempt history before requesting a manual rerun.
Manual required
The planned execution day has passed. An operator must request another run; it cannot enter the automatic queue.
Paused / Cancelled
An operator has suspended or cancelled eligibility. Review the audit and task controls.

A SUPERUSER or super administrator can set Maximum automatic attempts for an individual schedule from Edit schedule settings. The default is 3 total attempts, including the first run. For example, 6 attempts allows 5 retries. Failed runs may retry throughout the planned day, within the configured attempt limit. Automatic execution and retries stop after the planned execution day; later runs must be requested manually. A manual run preserves the original planned day and does not restart automatic retries on a later day. Existing confirmation, calendar and pause controls still apply.

When the worker is disconnected, live controls are unavailable and no success is assumed. Reconnect the worker and refresh. Errors stay visible until dismissed. Reset and evaluation-time overrides require a SUPERUSER and an operational reason.
